# HISTORY

결정과 변경을 날짜순으로 기록합니다. 새 항목은 아래에 추가합니다. 날짜는 한국 시간입니다.

## 2026-11-18

- **연구 방향 설정.** 선행 연구(OCR → 모델, 전사 점수)를 이어받아, OCR → 하네스 → 모델 조건에서 정답 대비 점수 상승이 유의한지 보는 연구로 정했습니다. 모델 성능 비교가 아니라 하네스 효과 측정이 목적입니다.
- **모델과 인증.** Claude Agent SDK를 구독 인증으로 사용하고, 본 실험 모델은 Sonnet으로 계획했습니다.
- **선행 연구 파악.** K-STR 크롭 1만 장 CER, KDoc 8쪽 문장 검사, Claude SDK 실행 기록을 확인했습니다. 긴 비전사 응답 2건이 Opus 실행 편집량의 85.9%를 차지한 사례에서, 출력 규약과 후처리가 점수를 크게 바꾼다는 점을 확인했습니다.
- **선행 문헌 조사.** OHRBench(OCR 오류가 RAG에 미치는 연쇄 영향), KLOCR/KOCRBench, Lost in the Middle, Adding Error Bars to Evals를 설계 근거로 삼았습니다.
- **구독 제약 확인.** 구독 로그인의 SDK 사용은 일반 구독 한도에서 차감됩니다. 1만 건 × 5조건(약 5만 회)은 완주를 보장할 수 없어, 약 2,000건 주 표본으로 검정력을 확보하는 안을 제안했습니다.
- **비용을 공동 종속변수로 추가.** 사용자 요청으로 입력·출력·캐시 토큰, 환산 비용, 정답 1건당 비용을 측정 대상에 넣었습니다. 선행 기록에서 호출당 약 25,000토큰의 숨은 캐시 컨텍스트와 보조 Haiku 사용을 발견해, 토큰을 출처별로 나눠 기록하기로 했습니다.
- **주 과제 확정.** 사용자 결정: 필드 추출 + 질의응답을 주 과제로, 전사 CER은 보조 지표로 합니다.
- **플랫폼 아키텍처 인사이트 적용.** aiagent_platform_core_system_architecture의 모델 경로, 오류 분류, 멱등성, Knowledge 계약, Guardrail, Memory, Observability, Evaluation 개념을 계약과 규칙 수준에서 적용하기로 했습니다. Identity, Credential Broker, 승인 절차는 가져오지 않습니다.
- **시스템 관점과 EDD.** 사용자 요청으로 일회성 연구가 아니라 평가 체계·비용 장부·대시보드를 먼저 세우고 그 위에서 연구를 수행하는 구조로 바꿨습니다.

## 2026-11-19

- **사용자 단계 플랜.** 데이터셋 선정 → 라벨링(사람 + AI) → Haiku 기준 점수 → 대시보드와 EDD 준비 → 하네스 구현 순서를 사용자가 제안했습니다. 보완점으로 지식베이스를 데이터와 함께 정하기, 라벨링 전에 정답 형식과 분할 고정, AI 초안은 Claude가 아닌 모델로, Haiku 점수는 파일럿으로 명시를 제안했습니다.

- **구현 플랜 v1 작성과 자체 평가.** 약점 9건을 찾았습니다. 가장 큰 위험은 지식베이스가 답을 대신 알려줘 점수 상승의 의미가 흐려지는 것입니다.
- **구현 플랜 v2.** 약점을 모두 반영했습니다. 1차(M0~M4, 기준선 세로 한 줄)와 2차(M5~M7)로 나누고, M1 앞에 탐색 두 가지와 관문을 두고, 질의 3종 구분과 CK(검색만) 대조군을 추가했습니다.
- **저장소 초기화.** CLAUDE.md, 연구 플랜, 구현 플랜, TODO, HISTORY를 작성했습니다.
- **설계 검토 피드백 반영 (v3).** 사용자가 전달한 검토 의견 세 가지를 받아들였습니다. (1) 주 지표를 "B 유형 중 OCR 오인식 필드의 정규화 정확 일치율"로 고정하고, OCR이 맞힌 필드를 망치는 비율을 동반 지표로 둡니다. (2) 첫 실험을 단일 턴 2×2(검색·구성 × 출력 후처리)로 바꾸고 이력 선별은 별도 실험으로 뺍니다. 후처리는 결정론적 후처리와 재질의로 구분합니다. CK는 정답 제품명을 주는 진단 조건으로 한정합니다. CLAUDE.md의 색인 금지 규칙을 금지 대상과 허용되는 공개 근거로 구체화했습니다. (3) 표본 규모는 M6 직후의 Sonnet C1·C4 짝지은 파일럿으로 정하고, 주 효과의 CI와 검정은 제품 단위로 계산합니다. 이유: 이전 설계로는 점수가 올라도 OCR 오류 교정인지, 검색에서 답을 가져온 것인지, 출력 형식 수정인지 구분하기 어려웠습니다.

- **착수 확정.** 사용자가 M0와 M1a 착수를 확정했습니다.
- **M0 저장소 골격.** Python 패키지(`src/ocr_harness`), 스키마 4종(항목·트레이스·평가 기록·비용 장부, JSON Schema), 스키마 검증 테스트, 저장소 검사(`repo_guard`: 데이터 파일 형식, 스키마 폴더 밖 JSON, 이메일, 촬영자 정보 키), GitHub Actions CI를 추가했습니다. 항목 스키마는 정의되지 않은 키를 거부해 촬영자 개인정보가 들어올 수 없게 했습니다. 비용 장부는 주 모델과 보조 모델, 인증 경로(구독·API 키·가짜 모델)를 구분해 적습니다.
- **M1a (가) 필드 복원.** 485장 전체에 자동 검사를 돌렸습니다. 제품명 155/182, 사용기한 142/177, 유효성분명 104/136(완전 일치)입니다. 라벨의 단어 순서가 읽는 순서가 아니어서 좌표로 줄을 다시 묶는 규칙을 넣었습니다 (완전 일치 38 → 104). 관문 판단: 제품명·사용기한·유효성분명은 "자동 추출 후 사람 확인"으로 진행, 용법·주의사항은 필드 정답에서 제외. B 유형 적격 필드는 약 337개(146제품)입니다. 자세한 숫자는 [m1a-results.md](m1a-results.md).
- **M1a (나) 식약처 매칭.** 의약품안전나라 공개 목록 95,269행과 맞춰 정확 133, 모호 15, 미매칭 4였습니다. 관문 판단: 정확 매칭이 다수이므로 M5에서 식약처 목록으로 지식베이스를 구축합니다. 성분·분량 근거는 품목 상세 정보를 따로 확보해야 합니다. 탐색 (나)·(다)는 클라우드에서 식약처 사이트와 PaddleOCR을 쓸 수 없어 사용자 PC에서 실행했습니다.
- **M1a (다) 로컬 OCR 집계.** PP-OCRv5 mobile로 485장을 돌려 B 유형 적격 338개 중 150개(113제품)가 OCR 오인식이었습니다. 제품명이 142/181, 유효성분명이 8/157입니다. 제품명 수치는 따로 검증해 실제 OCR 실패로 확인했습니다 (누락 45, 글자 다름 97, 큰 장식 글씨). 관문 판단: 진행. 단, 분모의 95%가 제품명이므로 첫 실험은 깨진 제품명의 교정을 재는 것이 되고, 검색은 제품명에만 의존하지 않게 설계합니다. 분모가 OCR 설정에 좌우되므로 M1b에서 설정 민감도를 확인한 뒤 엔진을 고정합니다.
- **M1a 완료.** 세 관문 모두 진행으로 판단했습니다. 다음 단계는 M1b(수집기)입니다.
- **스키마 설계안 v2 제안.** 사용자와 스키마를 검토하다가 v1(M0)이 근거 대조 없이 이름을 정한 곳이 많다는 점이 드러났습니다. OTel 규약에 없는 이름(`cache_creation`)을 썼고, 플랫폼 계약의 형식 규칙(camelCase, id·semver·traceId 패턴, 원문 기록 금지, 오류 코드 10종)과 어긋났습니다. 사용자 요청으로 플랫폼 계약 0.2.0과 OTel GenAI 규약(커밋 76e0c19)을 원문으로 대조해, 플랫폼에 그대로 넣을 수 있는 구조로 설계안을 다시 썼습니다 ([schema-design.md](schema-design.md)). 코드는 사용자 확인 뒤에 바꿉니다.
- **스키마 v2 확정과 구현.** 사용자가 설계안의 권고 5건을 모두 채택했습니다: (1) 봉투는 camelCase, 측정값은 `attributes` 안의 OTel 이름, (2) 버전은 semver(`eval-v1` → `1.0.0`), (3) trace를 OTel span 여러 줄로, (4) 플랫폼 계약 0.2.0 고정, (5) 신뢰구간·p값은 별도 통계 리포트에 두고 `evaluationId`로 연결. v1 스키마 4종을 지우고 8종(item, knowledgeDocument, conditionManifest, span, rawPayload, modelCall, fieldScore, evaluation)으로 바꿨습니다. evaluation과 knowledgeDocument는 플랫폼 계약 파일을 고치지 않고 그대로 쓰고, 테스트가 파일 해시를 원본과 대조합니다. span 속성은 닫힌 목록이라 원문이 들어가는 이름과 규약에 없는 이름(`cache_creation`)을 거부합니다. 스키마 버전 1.0.0을 `schemas/released/1.0.0.json`으로 동결했습니다. 이유: 플랫폼에 그대로 넣을 수 있는 형식을 실행 기록이 쌓이기 전에 고정하기 위해서입니다. v1 형식으로 만든 실행 기록은 없어서 옮길 데이터가 없습니다.
- **스키마 표준 대조.** 사용자가 스키마를 최대한 표준 규약에 맞추고 앞으로의 기준으로 삼겠다고 했습니다. OTLP(메시지 정의, JSON 인코딩, File Exporter), OTel GenAI 규약의 평가 이벤트와 메시지 스키마, Croissant 1.1을 원문으로 대조했습니다. 가장 큰 차이는 span이 이름만 OTel이고 형식은 OTLP가 아니라는 점입니다. 수정안 7건을 [schema-standards-review.md](schema-standards-review.md)에 적었고 사용자 확인을 기다립니다. 같은 날 사용자 요청으로 코드의 한글 주석을 보강했습니다.
- **스키마 2.0.0 (표준 형식).** 사용자가 표준 대조 수정안 7건을 모두 채택했습니다. (1) 추적을 OTLP JSON(File Exporter 형식)으로, (2) 건별 채점을 OTel `gen_ai.evaluation.result` 이벤트로, (3) 모델 호출 기록을 호출 1회당 chat span 하나로 합치고 비용 장부는 span에서 뽑는 집계로, (4) 저장하는 메시지를 OTel 메시지 JSON 스키마 구조로, (5) Croissant 설명 파일은 M1b에서, (6) 해시를 RFC 8785 정규화로, (7) 스키마에 `$id`와 한글 설명. 기록은 8종에서 7종이 됐습니다(span, modelCall, fieldScore → tracesData, logsData). 스키마 JSON이 길어져 원본을 `tools/build_schemas.py`의 표로 옮겼고, 테스트가 스크립트 결과와 파일이 같은지 검사합니다. 1.0.0 형식으로 만든 실행 기록은 없어 옮길 데이터가 없습니다. 이유: 사용자가 이 스키마를 앞으로의 기준으로 삼아 점진적으로 올리겠다고 했고, 1.0.0의 span은 이름만 OTel이고 형식은 OTel 도구가 읽지 못했습니다. 아직 확인하지 못한 것: 실제 OTel 수집기에 파일을 넣어 보는 검증(M3에서).
- **구조 점검.** 사용자 요청으로 함수의 공통화와 인터페이스·상속 구조를 점검했습니다. 고친 것: 필드 이름을 item의 `fieldId` 형식으로 통일(`product_name` → `product-name`. 밑줄은 플랫폼 id 패턴에 어긋남), 스키마 버전과 규약 커밋 상수를 `schema.py` 한 곳으로, 스키마 스크립트 안에서 두 번 적던 값 목록(인증 경로, 질의 유형)을 상수로. 미룬 것: 탐색 스크립트의 복사된 정규식과 라벨 읽기 중복은 M1b 수집 어댑터에서 정리. 인터페이스와 상속은 지금 없고, 구현이 둘 이상인 곳이 아직 없어 만들지 않았습니다. 사용자가 ponytail 규칙(가장 작은 변경, 요청받지 않은 추상화 금지)을 쓰기로 했고, 주석은 사용자 지시대로 한글로 넉넉히 유지합니다.

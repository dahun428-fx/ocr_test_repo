## 2026-11-18

- **연구 방향 설정.** 선행 연구(OCR → 모델, 전사 점수)를 이어받아, OCR → 하네스 → 모델 조건에서 정답 대비 점수 상승이 유의한지 보는 연구로 정했습니다. 모델 성능 비교가 아니라 하네스 효과 측정이 목적입니다.
- **모델과 인증.** Claude Agent SDK를 구독 인증으로 사용하고, 본 실험 모델은 Sonnet으로 계획했습니다.
- **선행 연구 파악.** K-STR 크롭 1만 장 CER, KDoc 8쪽 문장 검사, Claude SDK 실행 기록을 확인했습니다. 긴 비전사 응답 2건이 Opus 실행 편집량의 85.9%를 차지한 사례에서, 출력 규약과 후처리가 점수를 크게 바꾼다는 점을 확인했습니다.
- **선행 문헌 조사.** OHRBench(OCR 오류가 RAG에 미치는 연쇄 영향), KLOCR/KOCRBench, Lost in the Middle, Adding Error Bars to Evals를 설계 근거로 삼았습니다.
- **구독 제약 확인.** 구독 로그인의 SDK 사용은 일반 구독 한도에서 차감됩니다. 1만 건 × 5조건(약 5만 회)은 완주를 보장할 수 없어, 약 2,000건 주 표본으로 검정력을 확보하는 안을 제안했습니다.
- **비용을 공동 종속변수로 추가.** 사용자 요청으로 입력·출력·캐시 토큰, 환산 비용, 정답 1건당 비용을 측정 대상에 넣었습니다. 선행 기록에서 호출당 약 25,000토큰의 숨은 캐시 컨텍스트와 보조 Haiku 사용을 발견해, 토큰을 출처별로 나눠 기록하기로 했습니다.
- **주 과제 확정.** 사용자 결정: 필드 추출 + 질의응답을 주 과제로, 전사 CER은 보조 지표로 합니다.
- **플랫폼 아키텍처 인사이트 적용.** aiagent_platform_core_system_architecture의 모델 경로, 오류 분류, 멱등성, Knowledge 계약, Guardrail, Memory, Observability, Evaluation 개념을 계약과 규칙 수준에서 적용하기로 했습니다. Identity, Credential Broker, 승인 절차는 가져오지 않습니다.
- **시스템 관점과 EDD.** 사용자 요청으로 일회성 연구가 아니라 평가 체계·비용 장부·대시보드를 먼저 세우고 그 위에서 연구를 수행하는 구조로 바꿨습니다.

- **M1a (가) 필드 복원.** 485장 전체에 자동 검사를 돌렸습니다. 제품명 155/182, 사용기한 142/177, 유효성분명 104/136(완전 일치)입니다. 라벨의 단어 순서가 읽는 순서가 아니어서 좌표로 줄을 다시 묶는 규칙을 넣었습니다 (완전 일치 38 → 104). 관문 판단: 제품명·사용기한·유효성분명은 "자동 추출 후 사람 확인"으로 진행, 용법·주의사항은 필드 정답에서 제외. B 유형 적격 필드는 약 337개(146제품)입니다. 자세한 숫자는 [m1a-results.md](m1a-results.md).
- **M1a (나) 식약처 매칭.** 의약품안전나라 공개 목록 95,269행과 맞춰 정확 133, 모호 15, 미매칭 4였습니다. 관문 판단: 정확 매칭이 다수이므로 M5에서 식약처 목록으로 지식베이스를 구축합니다. 성분·분량 근거는 품목 상세 정보를 따로 확보해야 합니다. 탐색 (나)·(다)는 클라우드에서 식약처 사이트와 PaddleOCR을 쓸 수 없어 사용자 PC에서 실행했습니다.
- **M1a (다) 로컬 OCR 집계.** PP-OCRv5 mobile로 485장을 돌려 B 유형 적격 338개 중 150개(113제품)가 OCR 오인식이었습니다. 제품명이 142/181, 유효성분명이 8/157입니다. 제품명 수치는 따로 검증해 실제 OCR 실패로 확인했습니다 (누락 45, 글자 다름 97, 큰 장식 글씨). 관문 판단: 진행. 단, 분모의 95%가 제품명이므로 첫 실험은 깨진 제품명의 교정을 재는 것이 되고, 검색은 제품명에만 의존하지 않게 설계합니다. 분모가 OCR 설정에 좌우되므로 M1b에서 설정 민감도를 확인한 뒤 엔진을 고정합니다.
- **M1a 완료.** 세 관문 모두 진행으로 판단했습니다. 다음 단계는 M1b(수집기)입니다.
- **스키마 설계안 v2 제안.** 사용자와 스키마를 검토하다가 v1(M0)이 근거 대조 없이 이름을 정한 곳이 많다는 점이 드러났습니다. OTel 규약에 없는 이름(`cache_creation`)을 썼고, 플랫폼 계약의 형식 규칙(camelCase, id·semver·traceId 패턴, 원문 기록 금지, 오류 코드 10종)과 어긋났습니다. 사용자 요청으로 플랫폼 계약 0.2.0과 OTel GenAI 규약(커밋 76e0c19)을 원문으로 대조해, 플랫폼에 그대로 넣을 수 있는 구조로 설계안을 다시 썼습니다 ([schema-design.md](schema-design.md)). 코드는 사용자 확인 뒤에 바꿉니다.
- **스키마 v2 확정과 구현.** 사용자가 설계안의 권고 5건을 모두 채택했습니다: (1) 봉투는 camelCase, 측정값은 `attributes` 안의 OTel 이름, (2) 버전은 semver(`eval-v1` → `1.0.0`), (3) trace를 OTel span 여러 줄로, (4) 플랫폼 계약 0.2.0 고정, (5) 신뢰구간·p값은 별도 통계 리포트에 두고 `evaluationId`로 연결. v1 스키마 4종을 지우고 8종(item, knowledgeDocument, conditionManifest, span, rawPayload, modelCall, fieldScore, evaluation)으로 바꿨습니다. evaluation과 knowledgeDocument는 플랫폼 계약 파일을 고치지 않고 그대로 쓰고, 테스트가 파일 해시를 원본과 대조합니다. span 속성은 닫힌 목록이라 원문이 들어가는 이름과 규약에 없는 이름(`cache_creation`)을 거부합니다. 스키마 버전 1.0.0을 `schemas/released/1.0.0.json`으로 동결했습니다. 이유: 플랫폼에 그대로 넣을 수 있는 형식을 실행 기록이 쌓이기 전에 고정하기 위해서입니다. v1 형식으로 만든 실행 기록은 없어서 옮길 데이터가 없습니다.
- **스키마 표준 대조.** 사용자가 스키마를 최대한 표준 규약에 맞추고 앞으로의 기준으로 삼겠다고 했습니다. OTLP(메시지 정의, JSON 인코딩, File Exporter), OTel GenAI 규약의 평가 이벤트와 메시지 스키마, Croissant 1.1을 원문으로 대조했습니다. 가장 큰 차이는 span이 이름만 OTel이고 형식은 OTLP가 아니라는 점입니다. 수정안 7건을 `schema-standards-review.md`(2026-11-19 정리 때 삭제, git 이력에 있음)에 적었고 사용자 확인을 기다립니다. 같은 날 사용자 요청으로 코드의 한글 주석을 보강했습니다.
- **스키마 2.0.0 (표준 형식).** 사용자가 표준 대조 수정안 7건을 모두 채택했습니다. (1) 추적을 OTLP JSON(File Exporter 형식)으로, (2) 건별 채점을 OTel `gen_ai.evaluation.result` 이벤트로, (3) 모델 호출 기록을 호출 1회당 chat span 하나로 합치고 비용 장부는 span에서 뽑는 집계로, (4) 저장하는 메시지를 OTel 메시지 JSON 스키마 구조로, (5) Croissant 설명 파일은 M1b에서, (6) 해시를 RFC 8785 정규화로, (7) 스키마에 `$id`와 한글 설명. 기록은 8종에서 7종이 됐습니다(span, modelCall, fieldScore → tracesData, logsData). 스키마 JSON이 길어져 원본을 `tools/build_schemas.py`의 표로 옮겼고, 테스트가 스크립트 결과와 파일이 같은지 검사합니다. 1.0.0 형식으로 만든 실행 기록은 없어 옮길 데이터가 없습니다. 이유: 사용자가 이 스키마를 앞으로의 기준으로 삼아 점진적으로 올리겠다고 했고, 1.0.0의 span은 이름만 OTel이고 형식은 OTel 도구가 읽지 못했습니다. 아직 확인하지 못한 것: 실제 OTel 수집기에 파일을 넣어 보는 검증(M3에서).
- **구조 점검.** 사용자 요청으로 함수의 공통화와 인터페이스·상속 구조를 점검했습니다. 고친 것: 필드 이름을 item의 `fieldId` 형식으로 통일(`product_name` → `product-name`. 밑줄은 플랫폼 id 패턴에 어긋남), 스키마 버전과 규약 커밋 상수를 `schema.py` 한 곳으로, 스키마 스크립트 안에서 두 번 적던 값 목록(인증 경로, 질의 유형)을 상수로. 미룬 것: 탐색 스크립트의 복사된 정규식과 라벨 읽기 중복은 M1b 수집 어댑터에서 정리. 인터페이스와 상속은 지금 없고, 구현이 둘 이상인 곳이 아직 없어 만들지 않았습니다. 사용자가 ponytail 규칙(가장 작은 변경, 요청받지 않은 추상화 금지)을 쓰기로 했고, 주석은 사용자 지시대로 한글로 넉넉히 유지합니다.
- **OpenTelemetry SDK 직접 사용.** 사용자 제안으로 손으로 조립하던 OTLP JSON을 OpenTelemetry Python SDK(Apache 2.0)와 공식 JSON 인코더로 바꿨습니다. 확인한 것: SDK로 만든 span 6종과 평가 이벤트가 `tracesData`, `logsData` 스키마를 고치지 않고 통과합니다. 구조가 있는 속성(검색 문서 목록 등)도 그대로 실립니다. 일반 protobuf JSON 변환은 id를 base64로 내서 통과하지 못했고, 공식 JSON 인코더(`opentelemetry-exporter-otlp-json-common`)는 16진수로 냅니다. Python SDK에 OTLP JSON 파일 내보내기가 없어 그 부분만 직접 썼습니다(`JsonLinesSpanExporter`, `JsonLinesLogExporter`). 수집 서버는 여전히 두지 않습니다. 인코더와 로그 API가 베타라 버전을 고정했습니다. 테스트의 합성 기록도 SDK로 만들어, SDK 출력과 스키마가 어긋나면 테스트가 실패합니다.
- **오픈소스 도입 검토 문서.** 사용자 요청으로 직접 짜는 대신 오픈소스로 대체할 수 있는 부분과 이유를 [open-source-adoption.md](open-source-adoption.md)에 정리했습니다. 라이선스와 최신 배포일은 PyPI와 각 저장소의 LICENSE로 확인했습니다. 확인하다 고친 점: Arize Phoenix는 Elastic License 2.0이라 오픈소스 라이선스가 아니어서 후보에서 뺐습니다. `rank-bm25`는 마지막 배포가 2022년이라 `bm25s`를 골랐습니다. 기능이 우리 용도에 맞는지는 대부분 아직 확인하지 않았고, 각 단계에 들어갈 때 검증합니다.
- **저장 규칙을 고침.** "DB나 수집 서버는 두지 않는다"는 문장은 사용자가 정한 것이 아니라 저장소를 처음 만들 때 Claude가 써 넣은 설계 선택이었습니다. 사용자가 이를 물었고, 권고대로 "연구 기록의 원본은 JSONL 파일이고 서버는 그 파일을 읽는 보조 도구로만 쓴다"로 고쳤습니다. 이유: 스키마를 OTLP로 바꾼 뒤에는 뷰어와 검사 도구에 파일을 넣는 것이 자연스럽고, 원본이 파일로 남는 한 재현성은 그대로입니다.
- **Weaver, gitleaks, 추적 뷰어 판단.** 공식 문서를 원문으로 읽고 사용자가 권고를 채택했습니다. (1) Weaver는 M3 직전에 chat span 하나로 시험한 뒤 정합니다. live-check가 우리 JSONL 파일을 직접 읽지 못하고 OTLP protobuf 수신만 받기 때문입니다. (2) gitleaks는 도입하지 않습니다. 작성자가 기능 추가를 끝내고 보안 패치만 낸다고 공지했고 후속(Betterleaks)은 v2 개발 중입니다. 대신 GitHub의 Secret scanning과 Push protection을 켭니다(저장소 소유자 작업). (3) 추적 뷰어는 M3의 "실제 수집기에 넣어 보기" 때 가벼운 것 하나로 확인합니다. 조건별 점수·비용 비교는 뷰어가 아니라 M4 대시보드에서 집계합니다. 두 도구 모두 실제로 돌려 보지는 않았습니다.

- **실제 뷰어 확인 (합성 1건).** 사용자 요청으로 사용자 PC에 Jaeger v2.23.0(Apache-2.0, 공식 배포판, 체크섬 일치)을 띄우고, 실제 코드의 파일 내보내기로 만든 합성 추적(span 6개)을 넣었습니다. 확인한 것: 파일 한 줄을 고치지 않고 그대로 OTLP HTTP(4318, JSON)로 보내면 6줄 모두 200으로 받습니다. 서비스 이름, span 6개, 부모·자식 연결이 맞게 보이고, chat span의 토큰 속성을 Jaeger의 GenAI 화면이 입력·출력·캐시 토큰으로 인식합니다. 드러난 문제: 객체를 담은 배열 속성이 있는 span(retrieval, postprocess)을 화면에서 누르면 화면이 꺼집니다. 데이터는 API로 원래 모양대로 나오므로 저장은 정상이고 화면 표시 문제로 보이지만 원인은 추정입니다. 확인하지 못한 것: 평가 이벤트 파일, 다른 뷰어, 실제 실행 규모. 클라우드 작업 환경에서는 내려받은 뷰어 실행이 막혀 PC에서 했습니다.
- **코드를 공용과 전용으로 나눔.** 사용자 요청으로 `src/ocr_harness/`를 `common/`(schema, otlp, ledger, ids, repo_guard)과 `pharma/`(fields, kb_match)로 나눴습니다. 동작은 바꾸지 않고 위치와 import만 바꿨습니다. 공용 쪽에도 이 연구의 이름(`ocr.*` 속성, 서비스 이름, `img-` 접두사, `writer_num`)이 아직 박혀 있고, 무엇이 박혀 있는지 README에 적었습니다. 이 이름들을 인자로 빼는 일은 하지 않았습니다. 두 번째 프로젝트가 없는 지금 빼면 쓰임을 추측해서 설계하게 되기 때문입니다. 스키마 파일은 한 폴더에 그대로 두고 README 표에 공용·전용 구분만 적었습니다.
- **공용 계층에서 이 연구의 이름을 빼냄.** 바로 위 항목에서 미뤘던 일을 사용자 요청(인터페이스·상속·디자인 패턴을 적극적으로 써서 공용화)으로 했습니다. 공용 코드는 이름을 모르는 틀이 되고, 이 연구의 이름은 `ocr_harness/project.py` 한 곳에서 끼웁니다. 쓴 구조: 설정 객체 `Profile`, 스키마 출처의 전략(`FileSchema`, `SubSchema`)과 `SchemaRegistry`, 파일 내보내기의 템플릿 메서드(`JsonLinesWriter`), 상속으로 열을 더하는 `Ledger`, 규칙 객체를 조립하는 `RepoGuard`, 추상 기반 클래스 `FieldExtractor`와 그 자식 `PharmaFieldExtractor`. 테스트를 먼저 썼고(`tests/test_common.py`, 가상의 다른 프로젝트 설정으로 공용 틀을 돌림), 스키마 2.0.0과 동결 스냅샷은 바뀌지 않았습니다. 바뀐 호출 위치: `schema.validate` → `project.validate`, `ledger.model_calls` → `project.model_calls`, `otlp.resource` → `project.resource`, `ids.item_id` → `project.item_id`, `repo_guard.find_violations` → `project.find_violations`. 하지 않은 것: `kb_match.py`의 공용화(식약처 품목명 규칙이라 전용으로 둠), 스키마 생성 스크립트 `tools/build_schemas.py`의 공용화, 스키마 파일 폴더 분리.
- **PR #1, #2 병합, M1b 시작.** 사용자 승인으로 두 PR을 순서대로 병합했습니다. GitHub Secret scanning과 Push protection은 Claude의 권한으로 켤 수 없어 사용자 작업으로 남았습니다. - **OCR 엔진을 요인으로 둠.** 사용자가 "OCR을 Sonnet으로 하고 하네스 단계를 올리며 수치를 비교하면?"을 물었고, 결정 카드에서 "두 엔진 모두 (PaddleOCR + Sonnet)"를 골랐습니다. 이유: Sonnet이 얼마나 틀리는지 아직 몰라서, 하나로 바꾸면 고칠 필드가 너무 적어 유의성을 보이지 못할 위험이 있습니다. 둘 다 두면 어느 결과가 나와도 연구가 성립합니다. PaddleOCR을 로컬 OCR로 고른 것은 M1a 때 Claude의 선택이었고 사용자가 정한 것이 아닙니다. 아직 정하지 않은 것: Sonnet 엔진의 오인식 판정 규칙, 주 가설을 둘 엔진, 다중 비교 처리 (research-plan.md 조건 절).

# 연구 플랜

최종 수정: 2026-11-19

## 1. 연구 질문

같은 이미지, 같은 OCR, 같은 Claude 모델에서, OCR과 모델 사이에 기록 가능한 하네스(검색 → 컨텍스트 구성 → 이력 선별 → 후처리)를 넣으면 정답 대비 점수가 통계적으로 유의하게 오르는가. 그 상승은 어느 단계에서 나오고, 비용은 얼마인가.

- 모델 간 비교 연구가 아닙니다. 모델은 고정하고 하네스 구성이 독립변수입니다.
- 주 과제는 **필드 추출 + 질의응답**입니다. 전사 CER은 보조 지표입니다 (2026-11-18 확정).
- 첫 실험은 단일 턴에서 검색·컨텍스트 구성과 출력 후처리의 효과를 봅니다. 이력 선별은 별도 실험입니다.
- 일회성 실험이 아니라 평가 주도 개발(EDD) 체계로 만듭니다. 평가 체계와 대시보드를 먼저 세우고, 하네스 조건은 그 위에서 gate를 거쳐 들어갑니다.

## 2. 선행 연구에서 이어받는 것

선행 연구(`E:\ocr-local-benchmark`, 이 저장소에 없음)는 OCR → 전사 점수만 측정했습니다.

| 트랙 | 주요 결과 | 이번 연구에서의 쓰임 |
| --- | --- | --- |
| 합성 문서 12장 | PaddleOCR CER 0%, Qwen2-VL-2B 환각 다수 | 스모크 테스트 |
| K-STR 크롭 1만 장 | PaddleOCR micro CER 25.22%, EasyOCR 45.63% | 단어 크롭이라 RAG 효과를 보기 어려움 |
| KDoc-OCRBench-V2 8쪽 | 문장 검사 67개 중 PaddleOCR 56개 통과 | 보고서 도메인 후보 |
| Claude Agent SDK (구독 OAuth) | Opus 100장 CER 198.65%, 긴 비전사 응답 2건이 편집량의 85.9% | 출력 규약·후처리가 점수를 크게 바꾼다는 근거 |

이어받는 원칙: manifest 해시 잠금, 항목별 즉시 저장과 재개, 오류 별도 보존, 실패를 주 점수에서 빼지 않기, 개발용에서만 설정 선택.

## 3. 실험 조건

첫 실험은 **단일 턴**에서 "검색·컨텍스트 구성 유무 × 출력 후처리 유무"의 2×2로 맞춥니다. 요인이 하나씩만 달라지므로 검색과 후처리의 효과, 둘의 상호작용을 따로 추정할 수 있습니다.

| 조건 | 검색·컨텍스트 구성 | 출력 후처리 | 흐름 | 역할 |
| --- | --- | --- | --- | --- |
| C1 | 없음 | 없음 | OCR → 모델 | **기준선** |
| C2 | 없음 | 있음 | OCR → 모델 → 후처리 | 후처리 단독 효과 |
| C3 | 있음 | 없음 | OCR → 검색·구성 → 모델 | 검색 단독 효과 |
| C4 | 있음 | 있음 | OCR → 검색·구성 → 모델 → 후처리 | **전체 하네스** |

2×2 밖의 참고·진단 조건:

| 조건 | 구성 | 해석 범위 |
| --- | --- | --- |
| C0 | 이미지 → 모델(비전 직접) | 참고 기준. 주 분석에 넣지 않음 |
| CK | 정답 제품명만 주고 검색 → 모델 (OCR 텍스트·이미지 없음) | **진단용.** "제품을 이미 정확히 식별했다"는 가정에서 지식베이스가 답을 얼마나 제공하는지의 상한. CK가 맞힌 항목은 질의 종류별로 함께 보고하되, 주 분석의 분모는 CK 결과와 무관하게 사전에 고정 |

**출력 후처리**는 모델 출력 뒤에 적용하며 두 가지를 구분해 기록합니다.

- 결정론적 후처리: 정규화, 스키마·형식 검증. 모델 호출이 없으므로 모든 조건에서 "검사만" 모드로 돌려 적용 전·후를 둘 다 채점합니다.
- 재질의: 검증 실패 시 모델을 한 번 더 호출. 추가 호출의 토큰·비용·시간은 해당 조건에 귀속합니다. 재질의는 "검사만" 모드로 측정할 수 없으므로 C2·C4에서만 실행합니다.

**이력 선별은 별도 실험**으로 둡니다. 같은 문서에 대한 연속 질의 세션을 정의한 뒤, 이력 정책(없음 / 최근 N턴 / 관련 턴만 / 오염 이력)을 비교합니다. 첫 실험의 C4에는 포함하지 않습니다.

부 요인(일부 표본에서 하나씩 바꾸는 ablation): 검색기(BM25 / 밀집 / 하이브리드), top-k(1/3/5/10), 투입 순서(관련도 내림차순 / 역순 / 무작위 / 양끝 배치), 형식(평문 / 출처 태그 / JSON).

## 4. 질의·필드 3종

지식베이스에 해당 제품 정보가 있으면 모델이 이미지를 읽지 않고도 답할 수 있습니다. 그래서 모든 필드·질의에 종류를 붙이고 종류별로 따로 보고합니다. 종류는 모델을 돌리기 전에 정답·지식베이스·캐시된 OCR 출력만으로 정합니다.

| 종류 | 정의 | 예 |
| --- | --- | --- |
| A. 이미지에만 답이 있음 | 정답 값이 그 포장에만 있고 지식베이스에 없음 | 사용기한, 제조번호, 이 포장의 용량 |
| B. 지식베이스가 교정을 도움 | 정답 값이 포장에 인쇄돼 있고, 같은 용어가 지식베이스에도 있음 | 성분명·제품명·전문용어의 정확한 표기 |
| C. 둘 다 필요 | 이미지에서 제품을 식별한 뒤 지식베이스에서 답을 가져와야 함 | "이 제품의 유효성분은 어떤 계열인가" |

정답은 항상 **포장에 인쇄된 값**입니다. 지식베이스 값이 인쇄 값과 다르면(구 표기, 제형 차이) 인쇄 값이 정답이고, 지식베이스 쪽으로 "교정"한 출력은 오답입니다.

**OCR 오인식 필드:** 캐시된 OCR 출력에서 복원한 필드 값이 정규화 후 정답과 다른 필드(누락 포함). OCR은 모든 조건이 공유하므로 이 구분은 처리 이전에 정해집니다.

## 5. 변수

**독립변수:** 검색·컨텍스트 구성 유무, 출력 후처리 유무(2×2), 그리고 부 요인.

**관찰 변수(층화용):** 문서 도메인, OCR 난이도(항목별 OCR CER 또는 신뢰도 구간), 질의 종류.

**종속변수:**

- **주 지표(1개, 사전 등록): B 유형 중 OCR 오인식 필드에서의 정규화 정확 일치율.** 같은 필드에서 C4와 C1을 비교해 "하네스가 OCR 오류를 얼마나 복구했는가"에 답합니다.
- **동반 지표(해악 검사, gate):** OCR이 처음부터 맞힌 필드가 하네스 적용 후 틀린 비율. 주 지표만 보면 모든 값을 지식베이스 값으로 바꿔 쓰는 하네스가 유리해지므로 함께 판단합니다.
- 보조 지표: 환각률, 근거 인용 정확도, 거절·비전사 응답률, 필드 F1, 질의응답 ANLS, CER.
- 과정 지표: 검색 Recall@k·MRR, 정답 근거의 컨텍스트 내 위치, 제외된 이력의 정답 근거 포함률, 후처리 고침/망침 건수.
- 비용 지표(공동 종속변수): 입력·출력·캐시 토큰, API 환산 비용, 정답 1건당 비용, 지연 시간, 실패율.
- 안전성 지표: 이미지·문서 속 간접 인젝션 저항률, 개인정보 노출률.

**통제변수:** 모델 ID 고정(별칭 금지), Claude Code CLI·SDK 버전 고정, 도구 없음, 사용자 지정 system prompt, OCR 엔진·버전·캐시(모든 조건이 같은 OCR 텍스트 사용), 지식베이스 스냅샷, 작업 프롬프트 본문, 조건 실행 순서 무작위화. SDK는 temperature를 노출하지 않으므로 표본 5%를 3회 반복해 실행 간 변동을 측정합니다.

## 6. 가설

1. **H1(주 가설, 유일한 확증적 검정):** B 유형 OCR 오인식 필드에서 C4의 정규화 정확 일치율이 C1보다 높다.
2. H2: 검색·구성의 주효과가 있다 (C3 − C1, C4 − C2). 후처리의 주효과가 있다 (C2 − C1, C4 − C3). 둘의 상호작용도 추정한다.
3. H3: 하네스 이득은 OCR이 나쁜 항목에서 더 크다.
4. H4: 정답 근거가 컨텍스트 중간에 있을 때 정확도가 낮다 (순서 ablation).
5. H5: 하네스는 OCR이 처음부터 맞힌 필드를 허용 한계 이상으로 망치지 않는다 (비열등).
6. H6: 결정론적 후처리는 순효과가 양수지만 맞는 출력을 망치는 비율이 0이 아니다.
7. H7: C4는 건당 비용이 높지만 OCR 오인식 필드에서 정답 1건당 비용은 C1 이하이다.
8. H8: 검색은 정확도를 올리지만 검색 결과 검사가 없으면 오염 문서에 대한 취약성이 커진다.

이력 선별 가설(무관한 턴 제외는 이득, 관련 턴 제외는 손해)은 별도 실험에서 다룹니다.

### 보고 구성

| 평가 대상 | 보고할 결과 |
| --- | --- |
| B 유형 중 OCR 오인식 필드 | C4 − C1 정확도 차이와 95% CI (주 결과) |
| OCR이 처음부터 맞힌 필드 | 하네스 적용 후 오히려 틀린 비율 |
| A 유형 (사용기한·제조번호 등) | 이미지 고유 정보의 정확도 변화 |
| C 유형 질의응답 | 이미지와 외부 지식을 결합한 과제의 정확도 |
| CK가 맞힌 항목 | 종류별 건수와 비율 (진단) |

이 구성으로 선행 연구의 CER과 이번 연구의 필드 오류 복구율의 관계도 함께 설명합니다.

## 7. 통계 검정

한 제품에서 나온 여러 사진·필드는 비슷하게 맞거나 틀립니다. 그래서 분석 단위는 **제품**입니다.

- **주 효과:** C4 − C1 차이의 95% CI를 **제품 단위 짝지은 재표집**(같은 제품의 모든 필드를 함께 뽑음)으로 계산합니다. 검정도 같은 단위에서 합니다 (제품 단위 부호 뒤집기 순열 검정).
- **별도 분석:** 제품당 대표 항목 하나만 써서 독립성을 확보한 뒤 정확 McNemar 검정.
- 2×2 주효과·상호작용(H2), OCR 난이도 상호작용(H3): 혼합효과 로지스틱 회귀. 정답여부 ~ 검색 × 후처리 + OCR난이도 + (1 | 제품) + (1 | 필드).
- 해악 검사(H5): 비열등 한계 δ를 사전에 정하고 CI 상한과 비교.
- 보조 비교는 Holm-Bonferroni 보정. H1 외에는 탐색적 결과로 표기.
- LLM 채점자는 주 지표에 쓰지 않습니다(정규화 정확 일치는 규칙 채점). C 유형에 쓰면 200건을 사람이 채점해 Cohen's κ를 보고.

### 표본 규모

- 주 분석의 분모(적격 필드 목록)는 모델 실행 전에 고정합니다.
- 규모는 **Sonnet C1·C4 짝지은 파일럿**(M6 직후, 개발용 제품)으로 정합니다. 여기서 정오 불일치율(p_d), 제품별 편차, 건당 비용을 함께 잽니다. C0·C1만 있는 기준선 단계에서는 p_d를 잴 수 없습니다.
- 독립 짝 가정의 근사식 n ≈ (z_{1-α/2} + z_{1-β})² · p_d / Δ² 은 하한 참고값입니다 (p_d = 10%, Δ = 2%p이면 약 2,000). 실제 필요 규모는 파일럿의 제품 내 상관을 반영해 **제품 단위 검정력**으로 추정합니다.
- 추가 데이터는 이미지 총량과 함께 **새 제품 수**와 **제품별 B 유형 적격 필드 수**를 확인합니다.

## 8. 하네스가 기록할 것

모든 호출을 무상태(fresh query)로 두고 이력·문서·형식을 하네스가 직접 조립합니다.

| 단계 | 기록 항목 (JSONL) | 파생 지표 |
| --- | --- | --- |
| 입력 | item_id, 이미지 해시, 도메인, 난이도 태그, 질의, 질의 종류 | 층화 분석 |
| OCR | 엔진·버전, 원문, 줄별 신뢰도·좌표, 소요 시간 | OCR CER, 저신뢰 비율 |
| 검색 | 검색 질의문, 검색기·버전, 후보 documentId·점수·순위 전체, 채택 여부 | Recall@k, MRR |
| 컨텍스트 구성 | 최종 투입 순서, 형식 템플릿 id, 문서별 자른 길이, 구성요소별 토큰 | 정답 근거 위치 |
| 이력 선별 | 이전 턴 후보, 포함/제외와 제외 사유 | 제외된 턴의 정답 근거 포함률 |
| 모델 호출 | 전체 프롬프트와 해시, 모델 ID, SDK·CLI 버전, 원출력, 모델별 사용량, 오류·재시도, 시간 | 실패율, 거절률 |
| 후처리 | 규칙별 적용 전·후 diff, 스키마 검증 결과 | 고침/망침/무변화 |
| 채점 | 후처리 전 점수와 후 점수, 필드별 일치, 환각 판정 | 종속변수 |

## 9. 비용 측정

선행 연구 기록에서 확인한 사실:

- SDK 결과에는 항목별 입력·출력·캐시 토큰과 모델별 비용 메타데이터가 들어 있습니다.
- Opus 실행은 호출당 평균 약 25,000토큰을 캐시에서 읽었습니다. 프롬프트는 이미지 한 장과 짧은 지시뿐이어서, 대부분 SDK/CLI가 붙인 숨은 컨텍스트로 보입니다.
- 매 호출에 보조 Haiku 사용이 붙었습니다 (Sonnet 실행에서 보고 비용의 약 13%).

그래서 다음을 항목마다 기록합니다.

| 필드 | 출처 |
| --- | --- |
| 입력 / 출력 / 캐시 읽기 / 캐시 쓰기 토큰 | SDK 결과, 주 모델과 보조 모델 분리 |
| 컨텍스트 구성요소별 토큰 | 하네스가 직접 계산 (지시문, OCR 텍스트, 검색 문서, 이력, 이미지). 숨은 컨텍스트 = SDK 입력 합계 − 하네스 계산 합계 |
| SDK 보고 USD | SDK 결과. 구독에서는 청구액이 아닌 환산값 |
| 자체 계산 USD | 토큰 × 고정 단가표 (버전·날짜 기록) |
| 재시도 비용 | 실패 호출의 사용량 |
| 하네스 자체 비용 | OCR·임베딩·검색 시간 |
| 구독 한도 소모 | 실행 묶음 전후 사용량 화면 기록 (수동) |

분석: 조건별 건당 비용, 정답 1건당 비용, 증분 비용 효과비((C4 비용 − C1 비용) ÷ (C4 정답률 − C1 정답률)), 비용–정확도 파레토 곡선. 비용은 토큰 수, API 환산 USD, 구독 한도 소모율 세 가지로 구분해 보고합니다.

## 10. 구독 인증 제약

2026-11-18 기준 공식 도움말에 따르면 구독 로그인으로 쓰는 Agent SDK와 `claude -p`는 대화형 사용과 같은 구독 사용량 한도에서 차감됩니다. Max·Ultra·Team 플랜의 월간 API 크레딧은 연결된 Console 조직의 API 키로 실행할 때만 적용됩니다.

- 플랜별 호출 허용량은 공개돼 있지 않습니다. 파일럿에서 실측합니다.
- SDK는 내부 시스템 동작과 보조 모델 호출을 하네스가 완전히 통제하지 못합니다. 모든 조건에 동일하게 작용하지만 한계로 명시합니다.
- 장기간 실행 중 CLI가 갱신되면 조건이 바뀝니다. 버전을 고정하고 run 설정에 해시를 남깁니다.
- 데이터 이용약관이 외부 모델 전송을 허용하는지 확인이 필요합니다.

## 11. 플랫폼 아키텍처에서 가져오는 것

참고: [aiagent_platform_core_system_architecture](https://github.com/dahun428-fx/aiagent_platform_core_system_architecture). 플랫폼 스택은 띄우지 않고 계약과 규칙만 적용합니다.

| 플랫폼 개념 | 하네스에 적용 |
| --- | --- |
| Agent Gateway 모델 경로 | 모든 모델 호출이 한 함수만 통과. 비용 귀속, 경로 결정 기록 |
| 오류 분류 (RATE_LIMITED, UPSTREAM_TIMEOUT, UPSTREAM_ERROR) | 한도 도달·시간 초과·SDK 오류를 모델 오답과 분리 |
| 멱등성 키 | 키 = 항목 · 조건 버전 · 반복 번호. 재개 시 중복 호출 방지 |
| Knowledge 계약 (documentId, citation) | 지식베이스 문서에 고정 id 부여, 정답지의 근거 문서 id와 연결 |
| Guardrail ③ 검색 결과 검사 | OCR 텍스트와 검색 문서를 비신뢰 입력으로 취급, red-team 부분집합 |
| Guardrail 검사 모드 | 후처리를 "검사만" 모드로 전 조건 실행 |
| Memory 규칙 | 이전 대화를 Memory 구성요소로 분리, 오염 이력 조건 |
| Observability (OTel GenAI) | span·필드 이름을 규약에 맞춤 |
| Evaluation 결과 스키마 | 조건 × 지표마다 평가 기록, 데이터·버전·traceId 포함 |
| Manifest + Tuning | 조건을 불변 버전으로 선언, 개선은 새 버전 → 재평가 |

가져오지 않는 것: Identity, Credential Broker, 사람 승인, 테넌트 구분.

충돌하는 규칙: 플랫폼은 프롬프트·출력 원문을 기본적으로 기록하지 않지만 이 연구는 원문이 핵심 증거입니다. 평가 목적 예외로 보고, 원문 로그는 저장소 밖 별도 경로에 두고 보존 기간을 명시합니다.

## 12. EDD gate와 대시보드

후보 버전이 다음 단계로 가는 조건 (수치는 파일럿 후 확정):

| gate | 기준 예시 | 실패 시 |
| --- | --- | --- |
| 정확도 비열등 | 기준선 대비 주 지표 차이의 95% CI 하한이 −δ 이상 | 후보 폐기 |
| 안전성 | red-team 집합 인젝션 저항률이 기준선 이상 | 후보 폐기 |
| 비용 | 건당 토큰·환산 USD가 사전 상한 이하 | 경고 후 사람이 판단 |
| 실행 안정성 | 실패율이 상한 이하 | 원인 수정 후 재실행 |

대시보드 패널: 조건별 정확도와 CI, 단계별 기여, 비용(토큰 출처별·정답당 비용), 비용–정확도 파레토, 검색 품질, 후처리 영향, 실패 원인 분류, 안전성, 실행·한도, 회귀·드리프트. 모든 숫자에 데이터 버전을 표시하고 해당 run·항목 트레이스로 내려갈 수 있어야 합니다. 형태는 정적 HTML 생성기로 시작합니다.

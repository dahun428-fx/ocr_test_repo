# 오픈소스 도입 검토

작성 2026-11-19. 사용자 요청으로, 직접 짜는 대신 오픈소스로 대체할 수 있는 부분과 도입 이유를 정리했습니다.

## 1. 판단 기준

1. **표준이나 널리 쓰이는 구현이 있으면 직접 짜지 않습니다.** 직접 짠 코드는 우리가 고쳐야 하고, 표준 구현은 다른 도구와 바로 맞물립니다.
2. **연구 설계 그 자체인 부분은 직접 유지합니다.** 무엇을 정답으로 보고 어떻게 채점하는지는 이 연구의 결정이라 남의 도구에 맡기지 않습니다.
3. **도입할 때마다 검증 테스트를 하나 둡니다.** "이 도구의 출력이 우리 스키마를 통과한다" 같은 테스트가 있어야 도구 버전을 올릴 때 차이를 잡습니다.
4. **실제로 쓰는 단계에서 도입합니다.** 쓰기 전에 미리 넣지 않습니다.
5. **라이선스를 원문으로 확인합니다.** 이 저장소는 공개이고 플랫폼 저장소로 옮겨 갈 수 있습니다.

## 3. 이미 도입한 것

### OpenTelemetry Python SDK와 공식 JSON 인코더

- **대체한 것**: OTLP JSON을 손으로 조립하던 코드 (`otlp.py`의 쓰기 함수들).
- **도입 이유**
  - span id 생성, 부모·자식 연결, 시간 기록을 SDK가 합니다. 직접 짜면 틀리기 쉬운 부분입니다.
  - 형식이 표준과 어긋날 여지가 줄어듭니다. 실제로 일반 protobuf JSON 변환은 id를 base64로 내서 OTLP JSON 규칙(16진수)과 달랐고, 공식 인코더는 규칙대로 냅니다.
  - 플랫폼 저장소의 Observability와 같은 도구를 쓰게 됩니다.
- **확인한 것**: SDK로 만든 span 6종과 평가 이벤트가 우리 `tracesData`, `logsData` 스키마를 고치지 않고 통과합니다. 테스트의 합성 기록도 SDK로 만들어서, SDK를 올렸을 때 어긋나면 테스트가 실패합니다.
- **직접 남긴 것**: Python SDK에는 OTLP JSON 파일 내보내기가 없어 내보내기 클래스 2개만 썼습니다.
- **주의**: JSON 인코더(`opentelemetry-exporter-otlp-json-common` 0.66b2)와 SDK의 로그 API는 베타입니다. 버전을 고정했습니다.

### `rfc8785`

- **대체한 것**: 키 정렬로 흉내 내던 해시용 JSON 정규화.
- **도입 이유**: 숫자와 문자열 표기까지 RFC 8785가 정한 대로 해야 다른 언어로 구현해도 같은 해시가 나옵니다. 숫자 표기 규칙은 직접 구현하면 틀리기 쉽습니다.

### `jsonschema`, `referencing`

- **쓰는 곳**: 기록 검증. `referencing`은 OTel 메시지 스키마 사본을 네트워크 없이 `$ref`로 연결하는 데 씁니다.

## 4. 시험 후 결정할 것: OpenTelemetry Weaver

2026-11-19에 공식 문서(README, live-check, 레지스트리 검증·정의 문서)를 원문으로 읽었습니다. 실제로 돌려 보지는 않았습니다.

- **무엇인가**: OTel 시맨틱 규약을 정의하고 검사하는 공식 도구입니다. 속성과 span 정의를 YAML 레지스트리로 적으면 정의 검사(`registry check`, Rego로 자체 규칙 추가), 실제 기록과의 대조(`registry live-check`), 버전 간 차이(`registry diff`), 문서·코드 생성(`registry generate`)을 합니다. Rust 실행 파일이고 버전은 0.28.0입니다.
- **대체할 수 있는 것**: `tools/build_schemas.py`가 만드는 속성 이름 규칙. 지금은 속성 이름마다 값의 종류와 필수 여부를 JSON Schema로 풀어 쓰느라 추적 스키마가 약 180KB입니다.
- **도입 이유**
  - `ocr.*`, `platform.*` 속성을 OTel 규약과 **같은 형식**으로 정의하고, GenAI 규약 속성은 `ref`로 그대로 참조합니다. 나중에 플랫폼과 규약을 나눌 때 다시 옮기지 않아도 됩니다.
  - 버전을 올릴 때 바뀐 속성 목록을 자동으로 얻고, 설계 문서의 속성 표를 정의에서 만들 수 있습니다.
- **걸리는 점**
  - live-check의 파일 입력은 Weaver 자체 표본 JSON이고 OTLP JSON Lines가 아닙니다. OTLP로 받으려면 Weaver가 수신 포트를 열고 우리가 protobuf로 보내야 합니다(JSON 본문은 거절). 테스트 때 OTLP 전송 내보내기를 추가로 붙여야 합니다.
  - span 이름만으로는 어느 정의와 대조할지 모르므로 span 종류마다 matcher를 적어야 하고, 필수 속성 누락까지 잡으려면 `strict_attribute_groups`를 써야 합니다.
  - 1.0 이전 버전이라 명령과 형식이 바뀔 수 있습니다. pip로 설치되지 않아 CI에는 `setup-weaver` 액션, 사용자 PC에는 설치 파일이 필요합니다.
  - 속성만 봅니다. OTLP 구조, item, conditionManifest, rawPayload 검사는 JSON Schema로 계속 해야 해서 검증기가 둘이 됩니다.
- **판단 (사용자 채택)**: 지금은 도입하지 않습니다. M3 직전에 chat span 하나만 레지스트리로 옮겨 live-check까지 돌려 보고 정합니다. span 속성 60개, 평가 이벤트 속성 17개, span 7종을 모두 옮기는 일은 그 뒤입니다.

## 5. 단계별로 도입할 것

### M1b 수집: `mlcroissant`

- **대체할 것**: Croissant 1.1 데이터셋 설명 파일(`croissant.json`)을 직접 조립하고 검사하는 코드.
- **도입 이유**: MLCommons가 관리하는 공식 구현이고, 만든 파일이 명세에 맞는지 검사해 줍니다. JSON-LD를 손으로 쓰면 틀려도 알기 어렵습니다.
- **주의**: 라이선스와 출처 칸은 데이터 이용약관 확인이 끝나야 채울 수 있습니다.

### M3 채점과 실행: `jiwer`, `tenacity`

- `jiwer`: 보조 지표인 글자 오류율(CER) 계산에 씁니다. 편집 거리 계산과 정렬은 흔한 구현이라 직접 짤 이유가 없습니다. 선행 연구(`E:\ocr-local-benchmark`)의 CER 계산과 값이 같은지 먼저 맞춰 봐야 점수를 이어서 볼 수 있습니다.
- `tenacity`: 모델 호출 재시도에 씁니다. 재시도가 한두 줄로 끝나면 넣지 않습니다. 재시도마다 chat span을 남겨야 하므로, 라이브러리가 그 지점에 끼어들 수 있는지 확인합니다.
- **직접 유지**: 주 지표(정규화 정확 일치)의 채점기. 정규화 규칙이 곧 연구 설계입니다.

### M4 대시보드: DuckDB, 그리고 추적 화면

- **DuckDB**: JSONL 파일을 서버 없이 SQL로 바로 조회합니다. 조건별 점수, 비용, 제품 단위 집계를 직접 반복문으로 짜는 대신 씁니다. 파일 하나로 동작해서 따로 띄울 서버가 없습니다.
- **추적 화면은 선택지가 셋입니다.**

| 선택지 | 장점 | 부담 |
| --- | --- | --- |
| 직접 만든 정적 화면 | 서버 없음. 연구에 필요한 것만 보여줌 | 화면을 직접 짜야 함 |
| Jaeger (Apache-2.0) | 표준 추적 뷰어. OTLP를 받음 | PC에 뷰어를 띄워야 함. 점수와 비용 화면은 없음 |
| Langfuse (MIT, `ee/` 폴더 제외) | LLM 전용. 추적, 비용, 평가를 함께 봄. OTLP를 받는다고 알려져 있음 | 자체 운영에 DB 여러 개가 필요하다고 기억함. 가장 무거움 |

- 우리 파일(OTLP JSON Lines)을 뷰어에 넣으려면 OTel Collector의 파일 수신 기능을 거쳐야 할 수 있습니다. 확인하지 못했습니다.
- **판단 (사용자 채택)**: 규칙을 "연구 기록의 원본은 JSONL 파일이고, 서버는 그 파일을 읽는 보조 도구로만 쓴다"로 고쳤습니다. M3에서 가벼운 뷰어 하나로 우리 파일이 실제로 읽히는지 확인합니다. 조건별 점수와 비용 비교, 통계 검정은 어느 뷰어에도 없으므로 M4 대시보드에서 직접 집계합니다.

### M5 검색: `bm25s`, `kiwipiepy`, `rapidfuzz`

- `bm25s`: BM25 검색. `rank-bm25`도 후보였지만 마지막 배포가 2022년 2월이라 `bm25s`(2026년 10월 배포)를 고릅니다.
- `kiwipiepy`: 한국어 형태소 분석. 제품명과 성분명은 띄어쓰기가 제각각이라 공백으로 자르면 검색이 안 됩니다. M1a에서 OCR이 제품명을 크게 틀린다는 것이 드러났으므로(142/181), 글자 단위(n-gram) 토큰화와 비교해서 고릅니다.
- `rapidfuzz`: 틀린 OCR 글자와 품목명의 유사도 계산. 지금 `kb_match.py`는 정규화 후 완전 일치와 접두사 일치만 봅니다.
- **직접 유지**: "평가 정답이 색인에 들어가지 않았는지" 검사 (CLAUDE.md 규칙 3). 이 프로젝트 고유 규칙입니다.

### M7 통계: `scipy.stats`

- **대체할 것**: 부트스트랩 신뢰구간과 순열 검정을 직접 짜는 코드.
- **도입 이유**: 검정 구현의 오류는 결과를 통째로 틀리게 만들고, 눈으로는 알기 어렵습니다. 검증된 구현을 쓰는 것이 맞습니다.
- **주의**
  - 우리는 제품 단위로 묶어서 뽑아야 합니다(군집 부트스트랩). 제품별로 먼저 집계한 값을 넘기는 식으로 써야 하고, 이 부분은 테스트로 확인합니다.
  - 최신 scipy는 Python 3.12 이상이 필요합니다. 지금 패키지 설정은 3.11 이상이라 올려야 합니다.

## 6. 비밀값 탐지: GitHub 기본 기능 (gitleaks는 도입 안 함)

- **빈 곳**: `repo_guard.py`는 데이터 파일, 이메일, 촬영자 정보 키를 검사하지만 비밀값(API 키, 토큰)의 모양은 검사하지 않습니다.
- **gitleaks를 넣지 않는 이유**: MIT 라이선스이지만, 작성자가 README에 기능 추가를 끝내고 보안 패치만 낸다고 공지했습니다. 후속인 Betterleaks(MIT)는 v2 개발 중이라 안정판 전입니다. 공식 `gitleaks-action`은 v2부터 MIT가 아닙니다.
- **대신 하는 것 (사용자 채택)**: GitHub 저장소 설정에서 Secret scanning과 Push protection을 켭니다. 설치할 것이 없고 푸시 시점에 막습니다. 저장소 소유자만 켤 수 있습니다.
- 커밋 전 로컬 검사가 필요해지면 그때 Betterleaks 안정판을 다시 봅니다.

## 7. 도입하지 않는 것

### Inspect AI (평가 실행 틀 전체)

- 영국 AI 안전 연구소가 만든 평가 프레임워크입니다. 실행, 채점, 로그, 뷰어를 한 번에 줍니다.
- **도입하지 않는 이유**
  - 기록 형식이 그 도구의 자체 로그 형식입니다. 우리는 OTLP와 플랫폼 계약을 기준으로 잡았습니다.
  - 모델 호출을 Claude Agent SDK의 구독 인증으로 해야 하는데, 그 경로를 지원하는지 확인하지 못했습니다.
  - 단계별(OCR, 검색, 컨텍스트, 후처리) 추적과 비용 귀속이 이 연구의 핵심이라, 실행 흐름을 직접 쥐고 있어야 합니다.
- 다만 채점기나 뷰어의 설계는 참고할 만합니다.

### Arize Phoenix

- LLM 관측 도구이고 OTLP를 받습니다.
- **도입하지 않는 이유**: 라이선스가 Elastic License 2.0입니다. 소스는 공개돼 있지만 OSI가 인정하는 오픈소스 라이선스가 아니고, 서비스로 제공하는 것을 제한합니다. 연구용으로 쓰는 데는 문제가 없어 보이지만, 플랫폼 저장소로 옮겨 갈 것을 생각하면 Apache-2.0이나 MIT인 대안을 먼저 봅니다.

### 모델 가격표 (LiteLLM의 가격 목록)

- 환산 비용 계산에 커뮤니티가 관리하는 가격 목록을 쓸 수 있습니다.
- **도입하지 않는 이유**: 가격표는 연구 결과에 바로 들어가는 숫자라, 어느 날짜의 어느 가격을 썼는지 우리가 고정해야 합니다(`ocr.cost.price_table.version`). 목록을 참고해 우리 가격표 파일을 만드는 것은 괜찮습니다.

| 부분 | 이유 |

## 9. 확인하지 못한 것

- 표의 "미확인" 항목은 라이선스와 최신 배포일만 확인했습니다. 우리 용도에 맞는지는 각 단계에 들어갈 때 작은 확인 작업으로 검증합니다.
- Weaver와 gitleaks는 문서만 읽었고 실제로 돌려 보지 않았습니다. GitHub 비밀값 검사가 공개 저장소에 무료라는 점은 원문을 다시 읽지 않았습니다.
- Langfuse의 자체 운영 요건과 OTLP 수신, Jaeger와 Collector로 우리 파일을 읽는 방법은 기억에 의존해 적었습니다.
- Inspect AI가 구독 인증을 지원하는지는 확인하지 않았습니다.
